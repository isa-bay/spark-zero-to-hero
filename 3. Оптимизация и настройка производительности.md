## 1 Понимание планов запросов

### Чтение и интерпретация `explain()`
- **Базовый вывод**: `df.explain()` — показывает физический план.
- **Расширенные форматы**:
  - `explain("formatted")` — более детально, с описанием операторов.
  - `explain("cost")` — статистика по стоимости узлов (требуется включенный CBO, `spark.sql.cbo.enabled=true`).
  - `explain("codegen")` — план с фрагментами генерируемого кода (Whole-Stage CodeGen).
- **Как читать**:
  - Идти снизу вверх — от источников к результату.
  - Операторы, вызывающие shuffle, помечены `Exchange` (с hashpartitioning/singlepartition).
  - `Sort` — полная сортировка, часто перед оконными функциями или SortMergeJoin.
  - `BroadcastExchange` — подготовка broadcast-таблицы.
  - `Project` — выбор колонок; `Filter` — предикаты; `Scan` — чтение источника.

### Разница между логическим и физическим планом
- **Parsed Logical Plan** → **Analyzed Logical Plan** (с разрешёнными именами) → **Optimized Logical Plan** (после Catalyst) → **Physical Plan** (конкретные реализации: `BroadcastHashJoin`, `SortMergeJoin`, `HashAggregate` и т.д.).
- Логический план — «что» нужно сделать, физический — «как» Spark это реализует.

### Анализ узких мест
- **Exchange** (shuffle) — самая дорогая операция. Если видите несколько Exchange подряд, подумайте о переписывании запроса.
- **Sort** — может быть следствием оконной функции или SortMergeJoin.
- **BroadcastExchange** — хорошо для маленьких таблиц, но требует памяти драйвера и executor-ов.
- **Фильтры после shuffle** — Catalyst обычно применяет pushdown, но иногда порядок нарушен.

### Использование DAG визуализации в Spark UI
- На вкладке **Stages** можно увидеть DAG каждого задания.
- Каждая стадия соответствует границе широких зависимостей.
- Прямоугольники — этапы выполнения, стрелки — shuffle-данные. Помогает понять, где теряется время.


## 2 Партиционирование

### Понятие партиции
- Партиция — неделимая единица данных, обрабатываемая одной задачей.
- Количество партиций определяет степень параллелизма на стадии.
- **Факторы, влияющие на их количество**:
  - При чтении: определяется источником (например, блоки HDFS, количество файлов).
  - После shuffle: задаётся `spark.sql.shuffle.partitions` (по умолчанию 200).
  - После `repartition`/`coalesce` — явно указанное число.

### `repartition()` vs `coalesce()`
- **repartition(n)** — полный shuffle, равномерно перераспределяет данные. Может как увеличить, так и уменьшить число партиций.
- **coalesce(n)** — только сужение, без shuffle, объединяет соседние партиции. Быстрее, но может дать перекос данных, если партиции неравномерны.
- **repartition(cols)** — хэш-партиционирование по столбцам, shuffle.

### Настройки параллелизма
- `spark.sql.shuffle.partitions` — число партиций после операций shuffle (join, groupBy, оконные функции). Значение 200 — устаревшее для больших данных; правило: ~2–3 партиции на ядро executor-а, но не менее 1× общего числа ядер.
- `spark.default.parallelism` — для RDD операций, подобный смысл (по умолчанию равно общему числу ядер в кластере).

### Партиционирование при записи (`partitionBy`)
- `df.write.partitionBy("date")` — создаёт подкаталоги по значениям колонки.
- **Проблема “small files”**: когда каждое задание пишет свои файлы в каждую партицию, порождается множество мелких файлов. Решение:
  - Перед записью уменьшить число партиций через `coalesce` или `repartition`.
  - Использовать `maxRecordsPerFile` для контроля размера файлов.
  - Пост-компактирование (см. раздел «Работа с маленькими файлами»).

### Бакетирование (Bucketing)
- `df.write.bucketBy(16, "user_id").sortBy("user_id").saveAsTable("bucketed_table")`
- Хранит данные в фиксированном числе файлов (16), распределённых по хэшу ключа. При join двух таблиц с одинаковым числом buckets по тому же ключу Spark может выполнить Bucket Join без shuffle.
- Требует управления метаданными (Hive metastore). Эффективно для часто объединяемых таблиц с одинаковым ключом.
- Ограничения: число buckets фиксировано, изменение требует перезаписи таблицы.

### Диапазонное и хэш-партиционирование
- **Хэш-партиционирование** (по умолчанию в `repartition(col)`) — распределяет по `hash(key) % partitions`.
- **Диапазонное** (`repartitionByRange(col, n)`) — сортирует данные по ключу и разрезает на равные диапазоны; хорошо для отсортированных запросов, join с диапазонными условиями.


## 3 Управление памятью

### Архитектура памяти Executor
- **On-Heap**: управляется JVM, подчиняется сборщику мусора. Настраивается `--executor-memory` или `spark.executor.memory`.
- **Off-Heap** (Tungsten): память вне кучи, не управляется GC. Включается через `spark.memory.offHeap.enabled=true` и `spark.memory.offHeap.size`. Используется для кэширования и рабочих данных в бинарном формате.

### Области памяти
Внутри On-Heap/Off-Heap память делится (UnifiedMemoryManager):
1. **Reserved Memory** — 300 МБ, зарезервировано под внутренние нужды.
2. **User Memory** — (~40% от оставшейся) под пользовательские структуры (UDF, hash-таблицы).
3. **Spark Memory Pool** — (~60% от оставшейся) делится на две области:
   - **Execution Memory**: используется для shuffle, join, сортировок, агрегаций.
   - **Storage Memory**: для кэшированных данных и broadcast-переменных.
   Пул общий: при неиспользовании одной областью память может заниматься другой, но Storage может быть вытеснена Execution (но не наоборот, если `spark.memory.storageFraction` не превышен).

### Ключевые параметры
- `spark.memory.fraction` (по умолч. 0.6) — доля кучи, отдаваемая под Spark Memory Pool (из того, что осталось после Reserved).
- `spark.memory.storageFraction` (по умолч. 0.5) — минимальная доля памяти Spark Pool, зарезервированная под Storage (иммунитет от вытеснения Execution).

### Настройка сборщика мусора (GC)
- Для больших кучих (> 8 ГБ) рекомендуется **G1GC**: `-XX:+UseG1GC`. Настройки: `-XX:InitiatingHeapOccupancyPercent=35` для раннего старта.
- Альтернатива: Parallel GC (`-XX:+UseParallelGC`) с большим Eden space (`-XX:SurvivorRatio=8`).
- Мониторинг: в Spark UI на вкладке Executors можно видеть время GC (GCTime). Если > 5–10% от общего времени задачи — проблемы с GC.
- Инструменты: `jstat -gcutil <pid>` для мониторинга на узлах.

### Spill to Disk
- Если памяти Execution не хватает, Spark вытесняет промежуточные данные на диск (спиллинг). Признаки — высокая активность диска, падение производительности.
- Минимизация: увеличить число shuffle-партиций (меньше данных на задачу), настроить `spark.sql.shuffle.partitions`, увеличить память executor-ов.

### OutOfMemoryError: диагностика и решения
- **Типы**:
  - `Java heap space` — недостаточно On-Heap памяти.
  - `GC overhead limit exceeded` — GC занимает > 98% времени.
  - `Direct buffer memory` — нехватка off-heap памяти (для netty, shuffle).
- **Диагностика**:
  - Логи драйвера/executor-а, вкладка Executors в Spark UI (размеры памяти, spill).
  - Настройка `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path` для дампа.
- **Решения**:
  - Увеличить `executor-memory`, уменьшить `executor-cores` (меньше потоков на тот же объем памяти).
  - Увеличить число shuffle-партиций.
  - Использовать off-heap память для снижения давления на GC.
  - Оптимизировать запрос (избегать лишних shuffle).

### Настройка числа ядер и памяти
- **executor-cores**: обычно 4–5 ядер на executor (рекомендация из документации) из-за накладных расходов на HDFS пропускную способность, но для вычислительно ёмких задач можно больше.
- **executor-memory**: зависит от объёма данных; для агрегаций с большими группами требуется больше памяти. Общая рекомендация: 8–32 ГБ.
- Не делать слишком больших executor-ов (> 64 ГБ) из-за GC; лучше много средних.


## 4 Кэширование и сохранение

### `cache()` vs `persist()`
- `cache()` — эквивалентно `persist(StorageLevel.MEMORY_AND_DISK)` (для PySpark) или `MEMORY_ONLY` (для Scala DataFrame) — но рекомендуется явно указывать уровень.
- `persist(level)` — позволяет выбрать уровень хранения.

### Уровни хранения (Storage Levels)
| Уровень | Описание | Применение |
|---------|----------|------------|
| MEMORY_ONLY | В памяти как Java-объекты. Быстрый, но если не влезает — пересчитывается по мере необходимости. | Когда данные гарантированно влезают в память. |
| MEMORY_AND_DISK | В памяти, излишки на диск (сериализованные). | Стандартный выбор для повторного использования. |
| MEMORY_ONLY_SER | Как сериализованные байты (экономия памяти, но CPU на десериализацию). | Плотные данные, память дефицитна. |
| DISK_ONLY | Только на диске. | Когда память нужна для вычислений, а кэш используется для предотвращения повторного чтения из медленного источника. |
| OFF_HEAP | В off-heap памяти (Tungsten). | Требует `spark.memory.offHeap.enabled`. Уменьшает нагрузку на GC. |

### Сериализация в кэше
- По умолчанию используется Java serialization, медленный и объёмный. Рекомендуется включить **Kryo** (`spark.serializer=org.apache.spark.serializer.KryoSerializer`) — он будет применяться и для кэширования, когда уровень подразумевает сериализацию.

### Checkpointing
- `df.checkpoint()` — сохраняет DataFrame/RDD в надёжном месте (HDFS) и разрывает длинную lineage, предотвращая пересчёт с самого начала при сбоях.
- Отличие от persist: данные записываются в указанный checkpointDir (`spark.sparkContext.setCheckpointDir`), и lineage обрезается; persist сохраняет lineage, данные могут быть потеряны при падении executor-а и пересчитаны.
- Используйте checkpoint для итеративных алгоритмов и длинных цепочек, где стоимость пересчёта высока.

### Когда кэшировать, а когда нет
- **Кэшировать**:
  - Данные используются многократно (join нескольких запросов к одному DataFrame).
  - Итеративные алгоритмы (MLlib).
  - После дорогостоящего shuffle, если результат нужен несколько раз.
- **Не кэшировать**:
  - Данные читаются однократно.
  - Объём данных сопоставим с памятью всего кластера (риск OOM).
  - Фильтрация сильно сокращает набор — лучше применить фильтр до кэширования.


## 5 Оптимизация Shuffle

### Почему shuffle дорог
- **Сетевой ввод/вывод**: данные пересылаются между исполнителями.
- **Дисковый ввод/вывод**: shuffle-блоки записываются на диск.
- **Сериализация/десериализация**: объекты преобразуются в байты и обратно.
- **Барьер стадий**: все задачи предыдущей стадии должны завершиться перед началом следующей.

### Map-side combine
- В RDD: `reduceByKey(func)` объединяет значения на стороне map перед shuffle, в отличие от `groupByKey`, который пересылает все значения.
- В DataFrame Catalyst автоматически применяет объединение, где это возможно (агрегации с частичной агрегацией). Можно увидеть в плане как два этапа: `partial_aggregate` → `merge_aggregate`.

### Настройка буферов shuffle
- `spark.reducer.maxSizeInFlight` (по умолч. 48m) — максимальный объём данных, получаемых от одного reduce-запроса. При больших объёмах можно увеличить до 96m.
- `spark.shuffle.file.buffer` (по умолч. 32k) — размер буфера для записи shuffle-файлов на этапе map. Увеличение до 64k или 128k может улучшить производительность дискового ввода/вывода.

### Сжатие shuffle
- `spark.shuffle.compress=true` (по умолчанию) — сжимать map output файлы.
- `spark.io.compression.codec` — кодек: `lz4`, `snappy`, `zstd`. Zstd даёт лучшее сжатие, но чуть медленнее; LZ4 — быстрый компромисс.
- `spark.shuffle.spill.compress=true` — сжатие данных при spill на диск.

### Data Skew (перекос данных)
- **Обнаружение**: в Spark UI, на странице Stages, задачи одной стадии: если некоторые выполняются намного дольше (> 3x от медианы) или обрабатывают значительно больший объём shuffle-данных — перекос.
- **Техники борьбы**:
  1. **Salting (соление ключей)**: добавить случайную соль к ключу, разбив горячие ключи на несколько, с последующей реагрегацией.
     ```python
     df.withColumn("salted_key", concat(col("key"), lit("_"), (rand() * 10).cast("int")))
     ```
  2. **Разделение на горячие/холодные ключи**: обработать отдельно часто встречающиеся ключи с broadcast join.
  3. **AQE Skew Join Optimization** (автоматически в Spark 3.x) — разбивает перекошенные партиции на более мелкие.
- **Дополнительно**: настройка `spark.sql.adaptive.skewJoin.skewedPartitionFactor` и `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes`.

### Speculative Execution
- **Проблема**: медленные задачи («отстающие») из-за плохого железа, сетевых проблем и т.д.
- `spark.speculation=true` — включает предположительное выполнение: Spark запускает копию задачи на другом узле и использует результат того, кто завершится первым.
- Осторожно: может удвоить нагрузку на кластер; задайте порог `spark.speculation.interval`, `spark.speculation.multiplier`, `spark.speculation.quantile`.


## 6 Join-оптимизации

### Стратегии join
1. **Broadcast Hash Join (BHJ)** — одна из таблиц (меньше порога) передаётся целиком на все executor-ы, join выполняется без shuffle. Самый быстрый.
2. **Sort Merge Join (SMJ)** — основная стратегия для больших таблиц: shuffle по ключу, сортировка, затем слияние.
3. **Shuffled Hash Join (SHJ)** — shuffle + построение хэш-таблицы на одной стороне. Используется реже, когда одна из таблиц значительно меньше другой (но не помещается в broadcast). В Spark 3.x часто заменяется SMJ.
4. **Cartesian Join** — декартово произведение; очень дорогой, применяется, когда нет условий join.

### Выбор стратегии
- В Spark 3.x с включённым CBO (`spark.sql.cbo.enabled=true`) и собранной статистикой таблиц (`ANALYZE TABLE t COMPUTE STATISTICS`) выбор основан на стоимости.
- По умолчанию: если размер таблицы (в байтах) ≤ `spark.sql.autoBroadcastJoinThreshold` (10 МБ по умолчанию), то используется BHJ.
- Хинты: `/*+ BROADCAST(t1) */`, `/*+ MERGE(t2) */`, `/*+ SHUFFLE_HASH(t1) */`.

### Настройка broadcast порога
- `spark.sql.autoBroadcastJoinThreshold` можно увеличить до 100–200 МБ (в байтах), если памяти executor-ов достаточно. Но помните: broadcast-таблица хранится в Storage памяти каждого executor-а.

### Оптимизация перекоса при join
- **Солинг ключей** (как описано выше) — вручную.
- **AQE Dynamic Optimize Skew Join**: автоматически определяется перекошенная партиция и разбивается на подпартиции. Включается через `spark.sql.adaptive.skewJoin.enabled=true`.

### Bucket Join
- Если две таблицы забакетированы по одному ключу с одинаковым числом buckets и отсортированы, Spark может выполнить join без shuffle (Bucket Hash Join). Активируется, когда встречает bucketed таблицы и условие join соответствует ключу бакетирования.
- Требует `spark.sql.sources.bucketing.enabled=true` (по умолчанию).
- Применим для фактов и измерений, которые часто объединяются.

### Сбор статистики таблиц
- `ANALYZE TABLE table_name COMPUTE STATISTICS` — собирает базовую статистику (количество строк, размер).
- `ANALYZE TABLE t COMPUTE STATISTICS FOR COLUMNS col1, col2` — статистика по колонкам (min, max, distinct count, null count). Необходима для CBO.
- Статистика автоматически обновляется при записи через `INSERT`, но при ручных манипуляциях может устаревать.


## 7 Настройка сериализации

- **Java serialization** (по умолчанию): медленный, громоздкий, но не требует регистрации классов.
- **Kryo serialization**: значительно быстрее и компактнее. Включение:
  ```
  spark.serializer=org.apache.spark.serializer.KryoSerializer
  ```
  Для максимальной производительности нужно регистрировать классы:
  ```
  spark.kryo.registrationRequired=true
  spark.kryo.classesToRegister=com.example.MyClass
  ```
  Если класс не зарегистрирован, Kryo всё равно может его сериализовать, но с чуть большими накладными расходами (если `registrationRequired=false`). Рекомендуется включить требование регистрации в production и регистрировать все используемые пользовательские классы.


## 8 Адаптивное выполнение запросов (AQE)

### Основные фичи (Spark 3.x)
1. **Динамическое слияние shuffle-партиций** (`spark.sql.adaptive.coalescePartitions.enabled=true`): после стадии map автоматически объединяет мелкие партиции в меньшее количество, уменьшая накладные расходы на выполнение следующей стадии.
2. **Динамический выбор стратегии join** (`spark.sql.adaptive.localShuffleReader.enabled=true`): если после shuffle одна из таблиц оказывается достаточно маленькой, Spark может переключиться с SMJ на Broadcast Hash Join, экономя еще один shuffle.
3. **Динамическая оптимизация перекоса join** (`spark.sql.adaptive.skewJoin.enabled=true`): разбивает перекошенные партиции на подпартиции, чтобы равномерно распределить нагрузку.

### Настройка и мониторинг
- Включается по умолчанию в Spark 3.x: `spark.sql.adaptive.enabled=true`.
- Параметры:
  - `spark.sql.adaptive.coalescePartitions.minPartitionNum` — минимальное число партиций после объединения (не меньше, чем для параллелизма).
  - `spark.sql.adaptive.advisoryPartitionSizeInBytes` — целевой размер партиции (по умолч. 64 МБ). Можно увеличить для снижения числа задач.
- Мониторинг: в Spark UI на вкладке SQL можно увидеть, какие операции были адаптированы, например, "AdaptiveSparkPlan".


## 9 Динамическое выделение ресурсов

### Принцип работы
- Executor'ы запрашиваются при необходимости и освобождаются, когда простаивают (idle timeout).
- Требуется **External Shuffle Service** (ESS) для сохранения shuffle-файлов, сгенерированных выбывшими executor-ами.

### Настройка
- `spark.dynamicAllocation.enabled=true`
- `spark.shuffle.service.enabled=true` (и запустить ESS на каждом worker-узле, `start-shuffle-service.sh`).
- `spark.dynamicAllocation.minExecutors`, `maxExecutors`, `initialExecutors`.
- `spark.dynamicAllocation.executorIdleTimeout` — время простоя перед удалением (по умолч. 60 с).
- Для YARN: ESS встроен в NodeManager (настройка `yarn.nodemanager.aux-services`). Для Kubernetes: нужен отдельный shuffle-сервис (например, Spark Shuffle Service DaemonSet).


## 10 Работа с маленькими файлами

### Проблема “small files”
- Множество мелких файлов замедляет чтение (из-за большого числа операций открытия, метаданных), увеличивает нагрузку на драйвер (каждый файл — это потенциально отдельная партиция).
- Возникает при частых incremental-записях, использовании `partitionBy` с большим количеством значений.

### Компактирование файлов
- **Spark job**: `df.repartition(n).write...` для объединения.
- **Delta Lake**: `OPTIMIZE table` выполняет bin-compaction, объединяя мелкие файлы в более крупные (до target size).
- **Apache Hudi**: Clustering (асинхронная операция) или Compaction (для MOR таблиц).
- **Ручной подход**: периодическое чтение всего набора и перезапись с подходящим числом партиций.

### Настройка `maxRecordsPerFile`
- `df.write.option("maxRecordsPerFile", 1000000).parquet(path)` — ограничивает размер файлов, но не гарантирует отсутствие мелких файлов, если общее количество записей невелико.
- Совместно с `repartition` даёт контролируемый размер выходных файлов.

### Коалесценция перед записью
- Перед сохранением в файловую систему с партиционированием выполните `df.repartition(numPartitions, col("partition_key")).write.partitionBy("key")...`.
- Либо используйте `df.coalesce(desiredFiles)` для уменьшения числа файлов внутри каждой выходной партиции.
- Учитывайте: слишком сильное сжатие (мало файлов) может снизить параллелизм при последующем чтении.
