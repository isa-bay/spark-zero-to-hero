## 1 Введение в Spark

### Проблемы традиционной обработки данных (MapReduce)
- Высокая задержка из-за многократной записи на диск между стадиями Map и Reduce.
- Сложность программирования повторяющихся алгоритмов (итеративные вычисления, машинное обучение).
- Неэффективность для интерактивных запросов и потоковой обработки.
- Избыточный код на низкоуровневом API, отсутствие удобных абстракций.

### Что такое Apache Spark?
- **Распределённый движок обработки данных**, работающий в памяти (in-memory).
- Предоставляет унифицированный API для пакетной, потоковой, SQL и графовой обработки, а также машинного обучения.
- Ключевая идея: **Resilient Distributed Dataset (RDD)** — отказоустойчивая коллекция объектов, обрабатываемая параллельно.

### История создания и философия
- Разработан в AMPLab (UC Berkeley) в 2009 году, передан Apache Software Foundation в 2013.
- Создан как ответ на ограничения Hadoop MapReduce.
- Философия:
  - Единый стек для разнородных нагрузок.
  - Максимальное использование оперативной памяти.
  - Простой API на Scala, Java, Python, R и SQL.
  - Глубокая оптимизация выполнения через Catalyst и Tungsten.

### Области применения и версии Spark
- **ETL/ELT**: обработка больших объёмов структурированных и полуструктурированных данных.
- **Потоковая аналитика**: реальное время (Structured Streaming).
- **Машинное обучение**: обучение моделей, feature engineering, инференс.
- **Интерактивный SQL**: замена/дополнение хранилищ данных.
- **Графовая аналитика**: социальные сети, телеком.
- Версии: стабильные ветки 3.x, новейшая 4.0 (Preview). Важнейшие вехи: 2.0 (DataFrame/Dataset унификация), 3.0 (AQE, Dynamic Partition Pruning), 3.5 (Spark Connect, Python improvements).

### Плюсы и минусы Spark, сравнение с альтернативами

**Плюсы:**
- Скорость за счёт обработки в памяти и оптимизатора Catalyst.
- Универсальность: один движок для разных типов расчётов.
- Богатая экосистема (MLlib, Structured Streaming, GraphFrames).
- Лёгкость разработки: высокоуровневые абстракции (DataFrame/Dataset), SQL.
- Гибкое масштабирование и поддержка разных менеджеров кластеров.

**Минусы:**
- Потребление памяти: требует значительных ресурсов при больших объёмах.
- Не детерминированная задержка в реальном времени (лучше подходит для near-realtime).
- Сложность настройки под конкретные нагрузки (shuffle, memory).
- Не заменяет базы данных (нет транзакционности без Delta Lake / Iceberg).

**Сравнение с альтернативами:**
- *Flink*: лучше для истинно real-time стриминга (event-by-event, низкая задержка), сложнее в освоении.
- *Trino (Presto)*: ориентирован на быстрые SQL-запросы к множеству источников, не предназначен для сложных ETL и машинного обучения.
- *Snowflake / BigQuery*: облачные MPP-хранилища, Spark дополняет их как инструмент для трансформации и стриминга.


## 2 Установка и настройка

### Локальная установка (Windows, macOS, Linux)
- Требования: Java 8/11/17, Python 3.8+ (для PySpark), Scala 2.12/2.13 (для сборки).
- Загрузка дистрибутива с https://spark.apache.org/downloads.html.
- Распаковка, установка переменных окружения: `SPARK_HOME`, добавление `bin` в `PATH`.
- Проверка: `spark-shell` (Scala) или `pyspark` (Python).
- Под Windows может потребоваться winutils.exe для работы с Hadoop-подобной файловой системой.

### Настройка Spark в Docker-контейнере
- Официальные образы не предоставляются, но можно использовать:
  - `docker run -it apache/spark:latest` (для версий 3.x+).
  - Сборка собственного образа на базе OpenJDK + Spark + Hadoop libraries.
- Пример запуска кластера в Docker Compose: отдельные контейнеры для master и worker.
- Полезна для тестирования и CI/CD (Testcontainers для Spark).

### Подключение к облачным сервисам (EMR, Dataproc, HDInsight)
- **AWS EMR**: Spark устанавливается автоматически, интеграция с S3 через s3a коннектор. Настройка через кластерные конфигурации.
- **Google Dataproc**: быстрое развёртывание Spark/Hadoop, интеграция с GCS, Stackdriver-мониторинг.
- **Azure HDInsight**: управляемый Spark с интеграцией в ADLS Gen2, Azure SQL DB.
- Все облачные провайдеры поддерживают Jupyter, Zeppelin и инструменты мониторинга.

### Сборка из исходников и подключение Spark к IDE (IntelliJ, VSCode)
- Сборка: `./build/mvn -DskipTests clean package`.
- Для разработки на Scala в IntelliJ: sbt-проект с зависимостью `"org.apache.spark" %% "spark-sql" % "3.5.0"`.
- Для PySpark в VSCode: установить PySpark через pip, настроить `SPARK_HOME` и `PYTHONPATH`.
- Отладка возможна при запуске в локальном режиме (`local[*]`).

### Типовые конфигурационные файлы
- `spark-defaults.conf`: хранит настройки по умолчанию (master, memory, shuffle partitions и пр.).
- `log4j.properties` / `log4j2.properties`: управление уровнем логирования (WARN, INFO, DEBUG).
- `spark-env.sh`: переменные среды (JAVA_HOME, SPARK_MASTER_HOST, SPARK_WORKER_CORES и т.д.).
- `fairscheduler.xml` / `capacity-scheduler.xml`: для планирования очередей в YARN.


## 3 Архитектура кластера

### Компоненты: Driver, Executor, Cluster Manager
- **Driver**: основная программа, содержащая `SparkContext`. Преобразует пользовательский код в задания (Jobs), распределяет задачи (Tasks), собирает результаты.
- **Executor**: процесс на рабочем узле, выполняет задачи, хранит данные кэша/промежуточные shuffle-файлы. Каждое приложение имеет свои собственные executor-ы.
- **Cluster Manager**: управляет ресурсами кластера (YARN, Kubernetes, Standalone, Mesos). Выделяет контейнеры для executor-ов и драйвера.

### Жизненный цикл Driver и Executor
- **Driver**:
  1. Запуск `SparkContext` / `SparkSession`.
  2. Запрос ресурсов у Cluster Manager для executor-ов.
  3. Анализ DAG (логический план), разбиение на стадии.
  4. Отправка задач executor-ам, мониторинг выполнения.
  5. Завершение работы после выполнения или ошибки.
- **Executor**:
  1. Регистрируется в Driver.
  2. Получает задачи, выполняет их в многопоточном режиме (cores).
  3. Хранит кэшированные партиции и shuffle-данные.
  4. Отправляет heartbeat, отчитывается о статусе.
  5. Умирает при сбое узла или завершении приложения.

### Задачи (Tasks), стадии (Stages), этапы (Jobs)
- **Job** — работа, инициированная действием (action) в DAG (например, `df.count()`).
- **Stage** — набор задач, которые могут выполняться параллельно без shuffle. Границы стадии определяются широкими зависимостями (shuffle).
- **Task** — атомарная единица работы, обрабатывающая одну партицию данных. Выполняется в одном потоке executor-а.

### Режимы развёртывания (client vs cluster)
- **Client mode**: драйвер запускается на машине клиента (удобно для интерактивной разработки, но клиент должен быть рядом с кластером и всегда доступен).
- **Cluster mode**: драйвер запускается внутри кластера (менее чувствителен к разрывам связи, стандартный выбор для production-задач).

### Динамическое выделение ресурсов (Dynamic Allocation) — обзор
- Позволяет executor-ам запрашиваться и освобождаться динамически в зависимости от нагрузки.
- Требует внешнего shuffle-сервиса для сохранения shuffle-файлов после удаления executor-а.
- Конфигурируется параметрами: `spark.dynamicAllocation.enabled`, `spark.shuffle.service.enabled`.
- Позволяет экономить ресурсы в idle-периоды и масштабироваться при пиковых нагрузках.


## 4 Архитектура приложения

### SparkContext, SparkSession, SparkConf
- **SparkConf**: объект конфигурации (пары ключ-значение). Настраивает параметры приложения (имя, master, память и т.д.).
- **SparkContext**: точка входа для работы с RDD. Управляет соединением с кластером, создаёт RDD, аккумуляторы и broadcast-переменные.
- **SparkSession** (с версии 2.0): единая точка входа для DataFrame, Dataset и SQL. Объединяет `SparkContext`, `SQLContext`, `HiveContext`. Создаётся через `SparkSession.builder`.

Пример создания:
```scala
val spark = SparkSession.builder()
  .appName("MyApp")
  .config("spark.sql.shuffle.partitions", "200")
  .master("local[*]")
  .getOrCreate()
val sc = spark.sparkContext
```

### Spark UI и History Server
- **Spark UI**: веб-интерфейс (по умолчанию порт 4040), доступный во время работы приложения. Отображает:
  - Jobs, Stages, Tasks (DAG, длительность, объём shuffle, ввод/вывод).
  - Storage (кэшированные RDD/DataFrame).
  - Environment (версии, переменные, свойства).
  - Executors (потоки, память, задачи).
  - SQL (планы запросов).
- **History Server**: просмотр завершённых приложений. Запускается отдельно, читает event logs из настроенной директории (HDFS, S3). Необходимо задать `spark.eventLog.enabled=true` и `spark.eventLog.dir`.

### Логирование и конфигурирование для разных окружений (dev/stage/prod)
- Логирование настраивается в `log4j.properties`. Уровни: ERROR, WARN, INFO, DEBUG.
- Для production рекомендуется INFO для основных пакетов, WARN/ERROR для шумных библиотек.
- Конфигурации окружений выносятся в отдельные файлы `spark-defaults.conf` или передаются в `--conf` при запуске.
- Инструменты: комбинирование переменных окружения и профилей (Maven/sbt для Scala, конфиг-файлы для PySpark).


## 5 Основные абстракции данных

### RDD (Resilient Distributed Dataset)
- **Что такое RDD?**
  - Неизменяемая, распределённая коллекция объектов, разделённая на партиции.
  - Восстанавливается при сбоях с помощью lineage (последовательность трансформаций).
  - Работает на уровне объектов JVM (типизированный API).
- **Создание RDD**:
  - Параллелизация коллекции: `sc.parallelize(seq)`.
  - Загрузка из внешнего хранилища: `sc.textFile("hdfs://...")`, `sc.hadoopFile` и т.д.
  - Из существующего RDD трансформациями.
- **Трансформации и действия**:
  - *Трансформации* (ленивые): `map`, `filter`, `flatMap`, `distinct`, `union`, `groupByKey`, `reduceByKey`.
  - *Действия* (запускают вычисления): `collect`, `count`, `take`, `reduce`, `foreach`, `saveAsTextFile`.
- **Узкие и широкие зависимости**:
  - *Узкие (narrow)*: каждая родительская партиция используется не более чем одной дочерней (map, filter). Pipeline без shuffle.
  - *Широкие (wide)*: данные перераспределяются между многими партициями (groupByKey, join без специальных условий). Требуют shuffle и границу стадии.

### DataFrame
- **Отличие от RDD**: высокоуровневая абстракция с именованными колонками и схемой, оптимизируется Catalyst, работает на Tungsten-формате (off-heap). API бестиповый (Row).
- **Схема (StructType)**:
  - Определяется автоматически (inferSchema) или задаётся вручную.
  - `StructField` содержит имя, тип данных, nullable-флаг.
- **Реляционные операции**: `select`, `filter`, `groupBy`, `agg`, `join`, `orderBy` — похожи на SQL.

### Dataset
- Типизированная версия DataFrame: `Dataset[T]`, доступна только в Scala и Java.
- Сочетает преимущества RDD (типобезопасность, лямбда-функции) и DataFrame (Catalyst, Tungsten).
- Использует энкодеры (Encoders) для сериализации объектов в бинарный формат Tungsten.
- API: `map`, `flatMap`, `filter` с сохранением схемы.

### Сравнение RDD, DataFrame, Dataset — когда что выбирать

| Аспект | RDD | DataFrame | Dataset (Scala) |
|--------|-----|-----------|-----------------|
| Уровень абстракции | Низкий | Высокий (табличный) | Высокий (типизированный) |
| Оптимизация | Нет (только ручная) | Catalyst + Tungsten | Catalyst + Tungsten |
| Типобезопасность | Да | Нет (Row) | Да |
| Использование памяти | Объекты Java (overhead) | Off-heap / Tungsten | Off-heap / Tungsten |
| Производительность | Низкая | Высокая | Высокая |
| Языки | Scala, Java, Python | Все (через untyped API) | Scala, Java |
| Когда применять | Низкоуровневые операции, legacy, сложная обработка неструктурированных данных | Основной инструмент для ETL, SQL, ML (рекомендуется) | Когда критична типобезопасность и сложная логика в Scala |

**Рекомендация**: начинать с DataFrame, переходить на Dataset при необходимости строгой типизации в Scala. RDD – для особых случаев.


## 6 Физическое исполнение

### Жизненный цикл запроса: парсинг → анализ → оптимизация → физический план → генерация кода → выполнение
1. **Parsing**: SQL-запрос или операции DataFrame транслируются в необработанный логический план (Unresolved Logical Plan).
2. **Analysis**: с помощью каталога (Catalog) разрешаются имена таблиц, столбцов, проверяются типы → Resolved Logical Plan.
3. **Logical Optimization**: Catalyst применяет правила (predicate pushdown, constant folding, projection pruning) → Optimized Logical Plan.
4. **Physical Planning**: генерируются физические планы, оценивается их стоимость (cost-based), выбирается оптимальный → Physical Plan.
5. **Code Generation**: Whole-Stage CodeGen компилирует последовательности операторов в компактный Java-код, который исполняется напрямую, избегая виртуальных вызовов.
6. **Execution**: физический план преобразуется в DAG RDD, разбивается на стадии и задачи, выполняемые на executor-ах.

### Catalyst Optimizer
- Встроенный оптимизатор на основе функционального программирования.
- Правила разделены на **правила анализатора** и **правила оптимизатора**.
- Примеры: `PushDownPredicates`, `ConstantFolding`, `BooleanSimplification`, `ColumnPruning`, `CombineFilters`.
- Позволяет добавлять пользовательские правила (extensions).

### Tungsten
- Инициатива по улучшению производительности за счёт управления памятью вне кучи и кодогенерации.
- Ключевые особенности:
  - Хранение данных в бинарном формате (off-heap), что снижает накладные расходы GC.
  - Прямая работа с байтовыми буферами (sun.misc.Unsafe).
  - Whole-Stage CodeGen: слияние операторов в единый цикл, работающий на сгенерированном коде.
  - Компактные структуры для хранения строк и колонок.

### Predicate pushdown и column pruning
- **Predicate pushdown** — вынос фильтров на уровень источника данных (Parquet, JDBC) для сокращения читаемых данных.
- **Column pruning** — чтение только тех колонок, которые реально используются в запросе. Работает для колоночных форматов (Parquet, ORC).
- Эти оптимизации выполняются автоматически Catalyst и настройками источника.


## 7 Менеджеры кластеров

### Standalone
- Встроенный в Spark менеджер; запускается мастер-демон и рабочие узлы.
- Простейшая установка: `start-master.sh`, `start-worker.sh spark://master:7077`.
- Режимы: client (по умолчанию) и cluster.
- Ограничения: нет интеграции с другими фреймворками, ручное управление ресурсами.

### Hadoop YARN
- Основной менеджер в Hadoop-экосистеме; управляет ресурсами через ResourceManager и NodeManager.
- Два режима: `yarn-client` (драйвер на клиенте) и `yarn-cluster` (драйвер в Application Master).
- Позволяет запускать Spark вместе с MapReduce и другими YARN-приложениями.
- Хорошо подходит для организаций, уже использующих Hadoop.

### Mesos (историческая справка)
- Универсальный менеджер для различных фреймворков; Spark поддерживал Mesos с ранних версий.
- Сложен в настройке и эксплуатации; в настоящее время практически не используется в новых проектах.

### Kubernetes
- Современный стандарт: Spark нативно поддерживает K8s начиная с версии 2.3.
- Драйвер и executor-ы запускаются как поды; управление через `spark-submit` с мастером `k8s://https://<API-SERVER>`.
- Использование Spark Operator для декларативного управления приложениями (SparkApplication CRD).
- Преимущества: унифицированная оркестрация, изоляция, масштабируемость, совместимость с облачными сервисами.

### Сравнение и выбор менеджера

| Менеджер | Простота | Изоляция | Мультиарендность | Production-готовность | Рекомендация |
|-----------|----------|----------|------------------|-----------------------|--------------|
| Standalone | Высокая | Низкая | Нет | Для тестирования | Только для dev/PoC |
| YARN | Средняя | Средняя | Хорошая (Fair Scheduler) | Да (при наличии Hadoop) | Если уже есть Hadoop |
| Kubernetes | Средняя (растёт) | Высокая (поды) | Высокая (namespaces, quotas) | Да | Современный выбор, особенно в облаке |
| Mesos | Низкая | Средняя | Ограниченная | Практически нет | Не рекомендуется |


## 8 Системы хранения

### Подключение к HDFS, S3 (s3a), ADLS, GCS, локальной FS
- **HDFS**: `hdfs://namenode:8020/path`. Используется в кластерах Hadoop.
- **S3**: через s3a коннектор (`s3a://bucket/key`). Требует указания ключей доступа или IAM-ролей. Параметры: `spark.hadoop.fs.s3a.access.key`, `spark.hadoop.fs.s3a.secret.key`.
- **ADLS Gen2**: `abfss://container@storage.dfs.core.windows.net/path`. Аутентификация через OAuth2 / Storage Account Key.
- **GCS**: `gs://bucket/path`. Использует коннектор GCS.
- **Локальная файловая система**: `file:///path` (только для локального режима).
- Чтение/запись унифицированы через `spark.read.format("parquet").load("path")`.

### Важность локальности данных (Data Locality) и настройки `spark.locality.wait`
- **Data Locality** — запуск задач на том же узле, где расположены данные, чтобы избежать сетевого чтения.
- Уровни локальности (от лучшего к худшему): `PROCESS_LOCAL`, `NODE_LOCAL`, `RACK_LOCAL`, `ANY`.
- `spark.locality.wait` (по умолчанию 3с): время ожидания исполнителем освобождения ресурса на узле с данными перед тем, как пойти на более низкий уровень.
- Увеличение таймаута может повысить локальность, но задержит выполнение при нехватке ресурсов. Настройка компромиссная.

### Поддержка облачных объектных хранилищ: консистентность, коммиттеры
- **Проблема**: объектные хранилища (S3, GCS, ADLS) имеют конечную консистентность; переименование файлов — дорогая операция.
- **Решение**: специальные коммиттеры вывода:
  - *FileOutputCommitter* (по умолчанию): двухфазный коммит с переименованием (неэффективен).
  - *S3A Committer* (Staging, Magic) — для S3, позволяет избежать переименований.
  - *Databricks Cloud Committer* — оптимизирован под облачные хранилища.
  - *Apache Iceberg / Delta Lake* реализуют собственные коммиты через манифесты.
- Рекомендация: использовать оптимизированные коммиттеры для production-нагрузок на объектных хранилищах.
